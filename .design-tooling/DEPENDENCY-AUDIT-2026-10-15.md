# Design-tool dependency audit — 15 October 2026

**Result: known vulnerabilities found; OpenDesign runtime is on security hold.** The installation and earlier protocol checks remain recorded, but they are not security clearance. Project MCP is disabled and the local launcher refuses `start`, `mcp` and its scoped `codex` command. `stop`/`status` remain available. Offline Anthropic guidance, the project skill and copied craft references remain usable for research and planning.

No dependency versions, upstream source pins or lockfiles were changed. No exploit was executed, no model run was submitted and no website was created or audited. The daemon remains stopped.

## Scope and method

- OpenDesign **0.25.0**, commit `ae8038e7ce12ff305d57d12acbf3001f117cb100`: full workspace `pnpm audit --json` and a separate `pnpm audit --prod --json` view.
- Task-local runtime: `npm audit --json` against its `package-lock.json`, containing Node **24.22.0** and pnpm **10.33.2**. The npm audit CLI was **11.12.1**, run using the task-local Node executable.
- Audits used the public npm registry, an isolated executable/environment configuration and empty user/global npm configuration inputs. Only public dependency metadata was submitted; business media, website content and credentials were not submitted as audit input.
- Both audited lockfile hashes remained unchanged. All final audit responses were valid JSON with vulnerability results and no registry error. Exit status 1 means findings here, not a successful clean result. The first npm attempt failed because npm rejected loading `/dev/null` as both user and global config; retrying with two distinct empty local files succeeded. This initial configuration failure was not counted as a pass.
- Reviewed manifests, installed package metadata and selected source paths for operational relevance. This is dependency/advisory triage, not comprehensive data-flow analysis, penetration testing or proof of exploitability.

Raw reports and command metadata are under ignored `state/dependency-audits/`. The [reduced machine-readable report](DEPENDENCY-AUDIT-2026-10-15.json) retains package versions, all advisory records/ranges, dependency paths, direct declarations and raw-report hashes without lengthy advisory bodies or exploit samples.

The full report has **157 advisory records, 140 distinct GHSA identifiers and 40 affected package names**. Its record severities are 4 critical / 74 high / 64 moderate / 15 low. Some GHSA identifiers have separate version-range records or multiple affected package versions. The production-filter report has **142 records, 126 distinct GHSA identifiers and 34 affected package names**. Do not equate the 169 full findings with 169 independently exploitable bugs.

The runtime's one vulnerable `pnpm` package maps to **18 distinct advisories: 11 high and 7 moderate**. Do not describe that as only one advisory or add npm's package count to pnpm's finding count without explaining the different units.

`--prod` is a dependency-classification filter across the whole monorepo. It is **not** the selected daemon's deployment graph or proof of a reachable production endpoint. It includes dependencies of web/release/packaging tools that were not started. Manifest categories and actual feature use matter; for example Electron is a desktop `devDependency`, while packaging tools can declare their own runtime dependencies. The scanner's zero `devDependencies` metadata does not establish that the workspace contains no development dependencies.

## Remediation sequence and lifting the hold

1. Preserve the pinned evidence and offline references. Keep the runtime stopped and MCP disabled while selecting a supported patched OpenDesign release or a narrowly reviewed dependency update set. Do not blanket-apply audit fixes, unpin everything or approve optional install scripts just to remove warnings.
2. Address the package-manager findings and coordinated pin first, then the daemon upload/CSS/media/network dependencies needed for the intended features. Resolve Next/Electron/packaging findings before those surfaces are enabled or shipped. Record residual findings with specific applicability evidence; “dev-only” and “localhost” are not universal waivers.
3. Rebuild the affected closure and rerun both dependency scopes plus the runtime audit. Test the changed functional/security boundaries: malformed/aborted uploads, CSS map containment, bounded archive/image processing and relevant client authentication. Use benign local fixtures; no model run or business-asset upload is necessary for basic verification. Native/OS and provider checks need their own evidence.
4. Record versions, resolved/remaining advisories, applicability decisions and targeted results in a new audit/review entry. Only then change the explicit `SECURITY_HOLD` constant in `scripts/design-tooling.mjs` and re-enable the project MCP configuration. There is no environment-variable bypass or ignored state file whose deletion silently unlocks the runtime. Update source hashes/pins and rerun the relevant lifecycle/MCP checks after the reviewed change.

This is a maintenance sequence, not a request to start website implementation. Independent research, non-code design work and offline skill usage continue during the hold.

## Limits

Registry advisories change over time and can be corrected. This is the recorded snapshot, not a guarantee of complete vulnerability discovery. The scan did not audit Node's executable, macOS, browser engines, Codex itself, the npm audit CLI, all bundled/native/provider binaries, source-code security, configured cloud services or a future website's dependencies. An unreported package is not thereby certified safe. No compromise or exploitability of the local machine was established by these package findings.
