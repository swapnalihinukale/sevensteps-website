# Seven Steps motion and interaction specification

Proposed design specification, 15 October 2026. The user has explicitly requested detailed exploration of transitions, movement, shifts, arrows, scrolling and horizontal/vertical auto-motion. This document fulfils that planning scope. It does not implement the website or select its final visual identity. Every duration and speed below is a starting value to test, not a measured result or a browser guarantee.

Read with [DESIGN.md](../DESIGN.md), the [content assessment](CONTENT-ASSESSMENT.md), the [Indian benchmarks](INDIAN-BENCHMARK-RESEARCH.md) and the existing [performance envelope](INTERNATIONAL-AND-PERFORMANCE-RESEARCH.md). The latest motion request takes precedence over generic aesthetic advice against arrows or decorative movement. The earlier fast, lightweight, responsive requirement still applies. The answer is a richer coordinated motion system within that envelope, with a complete static experience.

## Recommended direction: a moving contact sheet

Use the photographer's own sequences (portraits, family interactions, rituals, celebrations and places) to give movement a subject. The memorable device is a photographic contact sheet that can be explored horizontally, opened into a full vertical story and optionally set in gentle motion. The site should feel like moving through an edited body of work, with a recognisable relation between overview, photograph and story.

The richest cohesive proposal combines an immediately visible lead photograph; one restrained opening gesture; a horizontal project rail with explicit arrows; image crossfades and a controlled lightbox; optional shared-image route transitions; quiet reading progress; polished menus and panels; and one optional moving filmstrip. The filmstrip can use a horizontal or vertical composition. Do not run both orientations, a rotating hero and an ambient video together. Richness comes from the connected behavior and precise response to the visitor, not from making every surface move simultaneously.

The complete wedding story remains an ordinary vertical document. Names, descriptions, service information and enquiry controls do not auto-scroll or wait for a reveal. A visitor can inspect every essential photograph and reach contact with motion off, a keyboard, a touch screen or a browser without the optional APIs.

### Three treatments to compare with the same real photographs

| Treatment | Distinctive movement | Best hypothesis to investigate | Tradeoff |
|---|---|---|---|
| **Moving contact sheet (recommended richest option)** | Horizontal project navigation; one optional moving strip; photograph-to-story continuity; calm panel transitions. | The observed mix of portraits, rituals and family moments benefits from a deliberate edit that invites exploration. | More interaction states and image preparation than a simple list. Needs a plainly visible route into each full story. |
| **A sequence of stills** | Fixed hero with manual crossfades, precise next/previous controls, vertical stories, short menu/dialog transitions. | Letting the photographs dominate may suit visitors who want to decide quickly. | Less ambient movement; still includes the requested detailed arrows and transition craft. |
| **Portraits in parallel** | A vertical decorative strip beside one static hero on sufficiently wide screens; horizontal/manual adaptation on narrow screens. | The photographer's portrait work may support a more composed, gallery-like first impression. | A second moving column competes for attention and bytes. It must disappear into a static/manual arrangement at small sizes. |

These are alternatives, not three modes to build by default. Typography, colours, exact images, publication permissions and the final concept remain subject to the main design brief. No new palette or typeface is needed merely to specify motion.

The prebuild review fixes the minimum index at two visible story links. Use those links without a project carousel. M04 remains an option if the portfolio grows; the first version can use photograph Previous/Next controls and one optional played strip. This preserves the requested arrow and motion craft without inventing a browsing problem. Test the Play/focus precedence in the lifecycle table with keyboard and pointer input.

## Global behavior and motion values

| Token / rule | Proposed value | Intended use |
|---|---|---|
| Immediate response | State and input acknowledgement without waiting for an animation | Navigation begins, a control changes state, or validation becomes available immediately. Effects confirm the change. |
| Press | 80–100 ms | Small button/icon depression; scale no smaller than 0.98. |
| Detail | 140–180 ms | Arrow shift, underline, icon orientation and local emphasis. |
| Panel entry / exit | 240 ms / 160 ms desktop; 200 ms / 140 ms compact layout | Menu, lightbox chrome and disclosure chrome; movement no more than 12–20 CSS px. |
| Image change | 360–450 ms desktop; 280–360 ms compact layout | Two-image opacity crossfade within a fixed frame. |
| Route continuity | 280–360 ms, cap 400 ms | Optional shared-image transition after a real navigation can render. Never add an artificial wait. |
| Opening gesture | 300–450 ms total, once per fresh entry | A small frame/caption accent around content already visible; no preloader or staged gate. |
| Settle easing | Cubic Bézier (0.22, 1, 0.36, 1) | Short translation into a stable resting state, without bounce. |
| Standard easing | Cubic Bézier (0.2, 0, 0, 1) | Most panel and local-control transitions. |
| Crossfade easing | Linear | Constant opacity exchange between prepared photographs. |
| Exit easing | Cubic Bézier (0.4, 0, 1, 1) | Brief dismissal; never prolong removal or block the next action. |
| Continuous strip speed | Horizontal 16 CSS px/s; vertical 10 CSS px/s | Optional image-only motion after explicit Play; adjustable through Slow/Normal controls. |
| Slow strip speed | Horizontal 8 CSS px/s; vertical 5 CSS px/s | User-selectable gentler movement. No automatic acceleration. |
| Still mode | Zero ornamental duration, displacement and auto-progression | Immediate, stable states with ordinary user-controlled scrolling and working controls. |

The curves are project proposals, not claims that one timing is scientifically optimal. Mobile travel distances and durations should reduce with the component's size; do not multiply every duration mechanically. Do not use elastic overshoot, repeated pulsing, flash/shutter flashes or bouncing typography for wedding photographs.

## Carousel, arrow and gallery details

- Use visible controls owned by the site: Previous, Next, Play/Pause where available, and a clear active position. The active counter is meaningful information, not decorative sequence numbering. Arrow buttons belong beside/below the frame on small screens so the photograph cannot camouflage them.
- Keep label text, hit areas and focus rings stationary. A three-pixel icon shift does not move the hit box. Never rely on a custom cursor, hover-revealed arrows, swipe alone, a tiny pagination dot or a drag instruction as the only navigation.
- A finite rail uses disabled start/end controls. A photo viewer should also be finite unless deliberate wrapping is selected and explained. Do not bounce back at the edge or reverse direction automatically. Direct selection must not send the user through intervening slides.
- Swipe navigation needs a clear horizontal intent and must release vertical movement to native page scrolling. Preserve pinch zoom, multi-touch, selection and ordinary browser gestures. Test diagonal motion, slow swipes, touch cancellation, stylus and trackpad use.
- Use native buttons and real links. Keyboard Tab reaches the controls in a sensible order. Enter/Space activates buttons; Left/Right is scoped to the focused viewer/rail where its behavior is clear. Do not globally capture arrow keys or interfere with a form field.
- In a true carousel only the active slide's interactive content is reachable; hidden slides must not remain accidentally focusable or be read as visible. A scrollable multi-card rail is different: its links remain a normal ordered set, and focused cards scroll into view. Do not apply a one-visible-slide accessibility model indiscriminately to both.
- For a manually changed image, one concise polite announcement may give its position and caption. Continuous auto-progression must not flood a live region. The rotation control precedes changing slide content in keyboard order. Follow the WAI carousel pattern rather than inventing a new role.
- A direct gallery URL, browser Back and reopening a lightbox must preserve a sensible selected image and reading position. Decide whether the viewer deserves URL state during implementation; do not create a history entry for every passive auto-advance.

## Automatic motion lifecycle

This section applies to optional hero rotation and to either filmstrip orientation. Manual browsing is the initial state. The user can explicitly choose automatic progression; it is not permission to start background video or scroll the page.

| State / event | Required behavior |
|---|---|
| Initial / no stored preference | Show a still photograph or stationary strip. Display Play and manual controls immediately. Do not load an automatic sequence just to prepare a timer. |
| Explicit Play | Start only if the component/control bar is visible, the page is foreground, the required next image is ready, Still mode is off and reduced motion is not requested. Preserve the current selection. Activation must work while Play retains focus or pointer hover; do not cancel it because those states already exist. |
| Hero rotation | Proposed 7-second dwell after an image is ready, followed by the M02 crossfade. At most one complete pass of the chosen three-image edit, then pause. No compulsory captions, price, service or enquiry text rotates with it. |
| Strip progression | Use the M17/M18 linear speed. Stop after one bounded pass by default. If looping is later selected, retain visible controls throughout and avoid an obvious snap at the join. Duplicated decorative images never create duplicated focus targets or repeated screen-reader content. |
| Pause | Freeze at the current visual position. Label changes to Play/Resume; no reset or crossfade occurs merely because Pause was pressed. |
| Stop/reset | Stop and return immediately to the first frame, as an explicitly labelled action. Keep Pause and Stop distinct. |
| Speed / direction change | Only affects the selected component. Change from the current position without a jump; direction change happens from a paused state. Expose named choices, not a speed slider as the only control. |
| New inspection hover/focus event | Pause and latch when the visitor enters to inspect or moves focus to another control/photograph. The existing focus/hover on an explicitly activated Play control does not cancel that request. Moving away or tabbing out does not restart. Resume requires an explicit action. |
| Swipe, drag, Previous/Next or direct image selection | Cancel automatic progression and retain the chosen image. Do not restart after a timeout. |
| Component leaves view / page becomes hidden / route changes | Stop timers, rendering loops and animation work. Preserve position and remain paused on return. Offscreen detection alone is insufficient for a background tab; use page visibility too. |
| Modal opens, device rotates or layout changes orientation | Pause the ambient component. Recalculate the static layout without translating a stale track distance; await explicit Resume. Never keep an obscured background animation running. |
| Next image is late or failed | Keep the current image visible. Stop automatic progression, offer retry/manual navigation and do not skip through errors silently. Do not start the dwell clock before the active image can actually be seen. |
| Reduced-motion setting changes while running | Stop immediately at a stable frame and apply Still mode. Do not animate back to a starting position. |

Proposed persistence: keep the site's Full/Still selection until changed, using a small local preference where available; a 30-day expiry is reasonable. Keep each component's paused/selected state for the current tab session, including route changes, Back and refresh where feasible. Never automatically resume a previously paused component on restoration. If storage is unavailable, default to still/manual. This preference is not analytics and should not contain personal or portfolio-client data.

The global setting has two explicit choices: **Full motion** and **Still**. The operating system's reduced-motion preference always makes the experience static, including when a previously stored Full selection exists. Do not silently override it. Still mode removes auto-motion, translation, scale, wipes, crossfades, animated scroll, progress tracking and route snapshots; controls commit to stable states immediately. Native scrolling initiated by the visitor and intentionally watched real films remain usable. A visible setting makes this choice accessible to people whose device setting is unavailable.

The W3C requirement for automatically starting moving/blinking/scrolling information is conditional: over five seconds, alongside other content and not essential; auto-updating information has a related rule without that five-second condition. This project supplies controls for **all** optional progression, even when user-started or short, so it does not depend on exploiting the threshold.

Container queries, fluid type and image crops should support the motion composition without becoming motion themselves. Use bounded fluid type with a readable minimum and maximum; do not animate font size or spacing during scroll. Set image aspect ratios and deliberate focal points, with mobile-specific art direction where the source permits it. Lightbox images should normally fit without cropping; cards/heroes may crop deliberately but must preserve faces, hands, rituals and context. Reflow should happen directly after a breakpoint/orientation change, with no animated rearrangement that a reader must chase.

## Speed, rendering and resource envelope

The motion request does **not** delete or replace the previously proposed budgets. The authoritative values and their measurement caveats remain in [International and performance research](INTERNATIONAL-AND-PERFORMANCE-RESEARCH.md). Carry forward these principal targets:

| Existing proposed target | Motion consequence |
|---|---|
| ≤350 KiB critical transfer before the main image can render; ≤900 KiB cold entry over the first 10 seconds at 390×844, no interaction/scroll | No preloader, full slideshow preload, automatic film player, animation font or hidden startup sequence. All automatic nearby image requests still count. |
| Initial JS ≤80 KiB compressed, CSS ≤30 KiB, HTML ≤35 KiB, fonts ≤100 KiB combined | Motion work consumes the same allowance. Candidate sub-budgets: ≤8 KiB of initial motion/control JS and ≤3 KiB of motion CSS **inside**, not on top of, those totals. Prefer native capabilities; no large animation framework merely to cover this repertoire. |
| First photo approximately 120–220 KiB mobile / 250–450 KiB desktop; deliberate full homepage ≤3 MiB; curated 25–35-image story ≤6 MiB | Image quality remains an editorial constraint. Share assets across views, load only useful neighbours, avoid originals and do not duplicate downloads for decorative copies. Optional user-started sequences still need a documented total. |
| Zero video/player bytes before explicit intent in the default mobile experience; no initial social/map/chat/film iframe | Still photographs carry first impression. Motion of a still image is not a reason to load a video. |
| Good field LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 at the 75th percentile | Lab traces guide decisions; they do not prove field results. Fixed media dimensions and responsive controls matter as much as transition duration. |

These are proposed project limits, not already achieved results. Per-resource allowances cannot all be consumed if their sum exceeds the critical total. Any exception needs the reason, measured impact, image-quality comparison and a lower-cost alternative in the existing decision record.

Prefer transform and opacity for small, bounded effects. They are not automatically free or guaranteed to stay on the compositor. Profile large crossfades, clipping and snapshot transitions on a mid-range device. Avoid animating width, height, margins, top/left positioning, large shadows, heavy blur, full-screen filters or font metrics. Use temporary promotion only where a trace shows benefit; do not leave every gallery image on a GPU layer or use blanket permanent `will-change` hints.

Keep at most one ambient component active and normally no more than two large photograph layers during a crossfade. Release listeners, timers, observers, snapshots and unneeded decoded image references on close/route change. Do not decode a whole story at once. If a per-frame loop is necessary for an explicitly played strip, use one scheduled loop, avoid alternating layout reads/writes, and stop it completely while paused, hidden or offscreen. CSS keyframes also need a real pause state; merely making the strip invisible is insufficient.

Compare the enhanced version against the same static composition, images and network conditions. On the agreed representative 60 Hz device, aim for work to fit its roughly 16.7 ms frame interval and inspect visible stutter and main-thread traces; do not advertise universal “60 fps.” Investigate motion-related long tasks over 50 ms, rising graphics memory, repeated decoding, battery/thermal load and an enquiry interaction that becomes slower while motion runs. If the image wipe, snapshot or strip is expensive, simplify that effect before compressing away important photographic detail.

## Implementation acceptance checklist (pending build authorization)

Use actual Chrome, Edge, Firefox and Safari/WebKit releases, recording versions. Include a real mid-range Android device, real iPhone/iPad Safari where available, touch and mouse/trackpad, and keyboard plus VoiceOver/TalkBack and a desktop screen reader. Emulation is useful but does not establish real iOS/Android behavior. Do not declare a feature supported merely because a laptop demo works.

Review outcome for this planning pass: the initial idea of adding motion to every section was narrowed to one photographic navigation language, with a broad repertoire of purposeful states and two alternative auto-motion orientations. The user's requested richness is retained. Continuous page scrolling, simultaneous ambient effects, repeated text reveals and unsupported “latest CSS everywhere” assumptions are excluded because they undermine the agreed fast, responsive and controllable experience.
